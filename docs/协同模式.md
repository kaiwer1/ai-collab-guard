# 同机多 AI 协同模式（方法论）

> 这是 **collab-guard 的伴随文档**：工具解决"巡检"，本文解决"这群 AI 怎么一起干活"。
> 由 DSH（DeepSeek Harness 会话）整理，依据多天真实协作记录；已脱敏（不含任何本地路径、业务名、账号信息）。

## 0. 前提约束（决定了所有设计）

同一台机器上同时运行多个 AI 会话（不同厂商、不同宿主动作）。它们：

- **没有共享内存**：各自维护自己的记忆/指令文件，互相看不见；
- **不能互相唤醒**：没有事件总线、没有 IPC 订阅；一个 AI 写完文件，另一个 AI 只会在**自己下一次被调度时**才发现；
- **宿主调度粒度不同**：有的最小 60 秒，有的只有小时级，有的平台的"分钟级"配置会被接受但**永不触发**。

⇒ 所有协同设计都必须建立在"**文件即状态、定时轮询即消息传递**"之上。

## 1. 三条通道（分级，不混用）

| 级别 | 通道 | 用途 | 为什么这样分工 |
|---|---|---|---|
| **① 主** | 本地聊天室（单机 HTTP 服务） | 认领、提问、交接通知、回执、实时讨论 | 秒级可见、零成本；但无编号、难检索 |
| **② 存档** | git 仓库里的"留言板"文件 | 正式记录、结论、判据、里程碑 | 有编号、可追责、可回溯；但提交会撞车 |
| **③ 按需** | 一个"灯"文件 + 各家收件箱文件 | 即时提醒指针、任务详情落盘 | 零依赖、不经 git；但不主动，需要被读 |
| 对外 | 具备 IM 出口的那个会话 | 仅两类事项通知人类 | 不打扰为默认，打扰为例外 |

**原则：结论进板（②），过程进聊天室（①），提醒进灯（③），打扰人只走 IM。**

## 2. 频率：按宿主能力，不强求一致

- 各会话自己上报频率，不要求统一；
- **改频率必须验证真的触发**（看第一次实际执行时间）——"接受配置"不等于"会执行"，这是最容易静默停摆的一步；
- 宁可错开分钟槽（例如 :02 / :17 / :25 / :40），也不要挤同一分钟抢同一个仓库。

## 3. 写权限：三条底线，不可同一人兼任

1. **改码**：只允许一个会话（"单写者"）。其他人只读、出判据、出交接说明。
2. **入库（commit/push）**：固定一个会话执行；它无额度时由指定备用手工代传，**commit message 必须注明"代传"**。
3. **验收**：必须由**实现者以外**的会话做（独立复跑 / 读码评审 / 端到端验收）。

> 为什么强调"不可兼任"：自己验收自己时，测试会不自觉地被写成"能过"，而不是"能抓错"。

## 4. 交接三件套（每次交付必须齐）

1. **交接说明**：状态、接收方、**精确文件清单**、行为说明、验证记录、**边界**（哪些没做/没验）、开发日志草稿。
2. **补丁入库**：只 `git add` 清单内文件；显式排除备份文件、音视频产物、临时文件。
3. **回提交号**：入库方回 commit hash；交接方同步后回执闭环。

没有第 3 步，任务会一直"待入库"，然后在某天变成两个人同时提交。

## 5. 验收五层（互相不可替代）

| 层 | 谁做 | 判据形态 |
|---|---|---|
| ① 自测 | 实现者 | 先红后绿的回归用例；静态检查全绿 |
| ② 独立复跑 | 另一个会话 | 干净克隆 + 指定 commit 跑全量测试，报 N/N |
| ③ 读码评审 | 第三个会话 | 逐条对照交接说明读 diff，指出"判据与实现不等价"处 |
| ④ 端到端 | 再一个会话 | 真入口（HTTP/CLI）跑一遍，量真实输出 |
| ⑤ 口径判据 | 业务相关方 | 数据口径可断言（档位、上下界、缺失值处理），不是"看起来对" |

**硬要求：反例必须会红。** 修复必须能证明打的是根因——把故障条件还原后必须复现失败；否则"全绿"可能只是因为测试没覆盖到。

## 6. 告警与通知分级

**被测系统的告警**
- **P0 静默改口径**：口径文件内容变了但版本号没变 → 立即上板"阻塞项"；
- **P1 正规升级**：内容与版本同变 → 板内记录；
- **P2 存量异常**：文件缺失/空文件/未登记 → 聚合一行，不逐条刷屏。
- 去重键：`文件路径 + 内容哈希 + 版本`；状态机 `pending → acked → resolved`；解除必须有回执，**不许静默消失**。

**通知人类的门槛（只有两类）**
- **A 决定不了**：影响范围 / 花钱或资源 / 对外可见动作 / 口径与验收标准的**定义权**（任一命中）；跨方无法收敛的分歧也算。
- **B 物理协助**：需要人到机器前、管理员权限、扫码/实体介质授权、线下操作等 AI 做不到的事。
- 其余（进展、验证通过、讨论过程、例行告警）**一律不打扰**。

## 7. 决策机制（人类不拍板时）

1. **多数 + 无硬性反对** 即定；
2. **硬事实优先于偏好**——"某参与方技术上不成立"是可复现事实，优先级高于任何偏好；
3. **定不下来就选成本最低、可回退的**；
4. **收敛时限 + 结论条固定格式**：`选哪个 / 谁部署 / 写入口规则 / 生效时间 / 回退方法`；
5. 结论只通知一次（防重复打扰）。

## 8. 踩坑清单（都是真实发生过的）

1. **编码**：在 Windows PowerShell 里用字符串直接发 HTTP body，中文会按 ANSI 编码变成 `?`。**必须** `UTF8.GetBytes(json)` + `Content-Type: application/json; charset=utf-8`；写文件用不带 BOM 的 UTF-8。
2. **定时陷阱**：平台的"分钟级"配置可能被接受但永不触发；改完频率要看第一次实际执行。
3. **临时目录陷阱**：某些打包进项目的 ffmpeg 二进制在写系统临时目录时会失败（返回 EIO），写项目内目录正常 ⇒ 用临时目录做产物目录的测试/生产路径会静默降级。
4. **优先级陷阱**：`a ? x : b ? y : z + w` 少了括号会把整块渲染吞掉——前端"看不见的东西"常常是表达式优先级。
5. **提交撞车**：多会话同时 commit/push 的窗口是秒级；先 fetch、单写者、立刻 push、被拒则 rebase 重放，绝不强推。
6. **代理**：本机代理经常失效，git 命令应显式直连。
7. **额度**：额度耗尽通常不报错，只是"停了"——靠心跳/余额上报才能发现。
8. **"完成"的定义**：单测全绿 ≠ 功能可用；必须端到端 + 反例 + 真机（用户机器）验证。

## 9. 与 collab-guard 的关系

- `collab-guard` 负责**巡检**：口径文件变更、记忆文件存在性、P0 告警与状态机；
- 本文负责**协作流程**：通道、频率、权限、交接、验收、通知门槛；
- 两者共同的前提是：**文件即状态**。所以当流程变化时，优先改文档、再改工具——工具只是流程的自动化。
